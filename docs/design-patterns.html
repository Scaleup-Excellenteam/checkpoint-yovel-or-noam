Design Patterns בפרויקט TSPO

Design Pattern הוא רעיון מוכר לארגון קוד ולפתרון בעיה שחוזרת בפרויקטים רבים. בפרויקט שלנו יש שני דפוסים מרכזיים שאפשר להציג.

1. Observer / Publish–Subscribe

הרעיון: משתמש נרשם לחדר. כאשר מתפרסמת הודעה, כל חברי אותו חדר מקבלים אותה.

משתמש שולח הודעה ← השרת מוצא את החדר ← ההודעה נשלחת לכל חברי החדר

איך מימשנו?

rooms שומר את החיבורים בכל חדר. join_room() מוסיף משתמש, ו־broadcast_to_room() מפיץ את ההודעה. בניתוק המשתמש מוסר מהחדר.

למה בחרנו?

השולח לא צריך להכיר את שאר המשתמשים. השרת מנהל את ההפצה ושומר על הפרדה בין החדרים.

חיסרון: החדרים נשמרים בזיכרון של שרת אחד. מערכת עם כמה שרתים תצטרך שירות משותף, למשל Redis Pub/Sub.

2. Strategy עם Dependency Injection

הרעיון: נותנים לרכיב לקבל דרך פעולה מבחוץ, כדי שיהיה אפשר להחליף אותה בלי לשנות את הרכיב עצמו.

IP נכנס ← בודק המוניטין מפעיל Report Fetcher ← מתקבלת החלטת אישור או חסימה

איך מימשנו?

IPReputationChecker מקבל פונקציה בשם report_fetcher. במערכת האמיתית היא פונה ל־VirusTotal; בבדיקות מחליפים אותה בפונקציה מזויפת שמחזירה תשובה מוכנה.

למה בחרנו?

אפשר לבדוק כתובת נקייה או זדונית בלי להיות תלויים באינטרנט, בלי לחשוף API key ובלי לבזבז קריאות VirusTotal.

חיסרון: כרגע מחליפים רק את מקור הדוח. כדי להחליף את כל שיטת ההחלטה יהיה צורך בממשק Strategy רחב יותר.

דפוסים נוספים: ממשק React מחולק לרכיבים קטנים, ו־Caddy משמש Reverse Proxy שמקבל HTTPS/WSS ומעביר את הבקשות לשרת Python. אלה דפוסים ארכיטקטוניים נוספים, אך שני הדפוסים המרכזיים להצגה הם Observer ו־Strategy.
